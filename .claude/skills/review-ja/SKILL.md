# 画面の文言の見直し

textlint（`npm run lint:ja`）は表記と機械的な規則を見る。このスキルは、textlint で拾えない**読みやすさ**を人の目の代わりに見る。**ファイルは書き換えない**。指摘と言い換えの案を出し、どれを直すかはユーザーに任せる。

## 1. 見る範囲を決める
- 指定がなければ、まだコミットしていない変更とブランチの変更を見る：
  ```bash
  git diff main...HEAD -- app/src/shared/strings/ja.ts
  git diff HEAD -- app/src/shared/strings/ja.ts
  ```
- どちらも空なら、ユーザーに「ja.ts 全体を見るか」を聞く
- 先に `npm run lint:ja` を動かし、textlint の指摘があればそれも一緒に伝える（このスキルでは同じ指摘を繰り返さない）

## 2. 文言ごとに読む
変わった値（関数なら、ありそうな引数を入れた結果）を、**画面のどこに出るか**を思い浮かべて読む。キーの名前と、その上のコメントが手がかりになる（`widget.*` はウィジェット、`settings.items.*` は設定画面の説明、`tooltip.*` はツールチップ）。

次のものを指摘する。
| 種類 | 例 | 言い換えの方向 |
|---|---|---|
| ぎこちない言い回し | 「〜を行う」「〜することができる」「〜となる」 | 動詞を直接使う（「〜する」「〜できる」「〜になる」） |
| 硬い漢語 | 「実施」「表示中の当該セッション」「押下」「既存」 | 和語や短い言葉（「する」「開いているセッション」「押す」「今の」） |
| 意味の通りにくい文 | 主語や目的語が抜けて何のことかわからない、修飾が長く係り先がわからない | 語を足す、文を分ける、順番を変える |
| 常体の過去形の文 | 「ビルドできなかった。」「設定を保存した。」 | 感想のように読める。お知らせは「です・ます」（「ビルドできませんでした」）、状態なら現在形（「保存済み」） |
| 補足や説明が多すぎる | ラベルに（ ）の補足、ツールチップの「押すと」「クリックで」、設定の説明に見ればわかる結果や中の仕組み | 補足を削る。ラベルは短い名詞、ツールチップは押すと起きることだけ、設定の説明は何が変わるかを 1 文で |
| 画面との食い違い | ボタンの名前と説明で呼び方が違う、同じものを別の言葉で呼ぶ | 一方にそろえる（`app/text/terms.yml` に足す案も出す） |
| 作風からの外れ | 短い説明が「。」で終わる、半角の英数字の前後に空白がない、お知らせや空の状態の文が「です・ます」でない、ラベルや説明が「です・ます」 | `docs/strings.md` の作風に合わせる |

指摘しないもの：
- 好みの範囲の言い換え（どちらでも同じくらい読みやすいもの）
- 製品名、コマンド名、ブランチ名など、画面にそのまま出す固有の文字

## 3. 伝える
文言ごとに次の形で並べる。急ぐもの（意味が通らない）から順に。
```
- `settings.items.zoom.description`
  今：「…」
  気になる所：…（なぜ読みにくいか、1 文で）
  案：「…」
```
最後に、直すものをユーザーに選んでもらう。選ばれたものだけを `ja.ts` で直し、`npm test` を通す。直さなかったものは、そのままにする。
